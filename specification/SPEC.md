## Resolved this pass

- **Low baseline FPS investigation (base ~40 FPS vs field ~70-80 FPS, no shaders; persists with shaders too, just offset by ~15-20 FPS) - general optimization pass, not a single reproducible crash/stutter bug** like the ScorchedGuns case. Captured and compared multiple `/sparkc profiler start` profiles (base vs field, Render-thread-only and later full multi-thread) and aggregated hot classes by mod package (not just individual method pairs, which dilutes a mod's true total cost across many differently-named methods) to get an honest picture. No single dominant outlier found at the base beyond what's expected for the mod count - broadly spread across `com.simibubi.create`, `traben.entity_model_features`, `java.lang.invoke`+`net.neoforged.bus` (event dispatch machinery), `software.bernie.geckolib`, `xaero.hud.minimap`, `foundry.veil`. Tried `/flywheel lightSmoothness FLAT` (Flywheel's own config explicitly flags `lightSmoothness` as having "a large performance impact") and lowering Simulation Distance - user reports neither made a meaningful difference, so the FPS floor here isn't dominated by either of those.
  - **`org.violetmoon.zetaimplforge.event.ForgeEventsRemapper` (Zeta, Quark's shared library) investigated as a candidate** - appeared consistently in every single profile captured (base, field, full multi-thread), independent of location, matching the user's "even looking at the ground, outside the building" observation (tick-driven, not view-frustum-dependent, since `ClientTickEvent$Post` is one of the events it wraps).
  - **Initially suspected as a missing-cache bug** (same shape as ScorchedGuns), but **verified via `javap` against the real deployed `Zeta-1.1-40.jar` bytecode first, and the suspicion was wrong**: `remapEvent()` (the per-event-firing method) does `zetaToForgeMap.get(eventClass)` - a map **already populated once**, at mod-init registration time via `registerWrapper(...)` → `findForgeWrapper(...)`, which is where the expensive class/constructor resolution actually happens. That part is NOT re-run per event; it's a genuine one-time cost already, same shape as the Zeta's own `isEntityModelFeaturesLoaded()`-style caching pattern seen in the ScorchedGuns investigation, just in a different mod. No newer Zeta version available (already on latest, `1.1-40` = current on Modrinth) and no config option exists to disable the Forge-compat layer; no open upstream issue found mentioning this either.
  - **What's actually left to optimize, once the false lead was ruled out**: the registered wrapper's `lambda$findForgeWrapper$4(Constructor, Class, Event)` calls `ctor.newInstance(new Object[]{event})` on every event firing - this part **is** architecturally required per-event (a fresh wrapper object is needed for each event instance; the object itself isn't cacheable), but the mechanism used to construct it (classic `java.lang.reflect.Constructor.newInstance`) carries more per-call overhead than a pre-resolved `java.lang.invoke.MethodHandle` would for the exact same constructor (an access check plus `InvocationTargetException` wrapping on every call, which `Constructor.newInstance` does regardless of how many times it's been called before).
  - **Fix, built on explicit request after setting expectations that the gain is modest** (not a dramatic "missing cache" win like ScorchedGuns - this is a narrower reflection-call substitution): `@Redirect` on `ForgeEventsRemapper.lambda$findForgeWrapper$4`'s `Constructor.newInstance([Ljava/lang/Object;)Ljava/lang/Object;` call, replacing it with a `ConcurrentHashMap<Constructor<?>, MethodHandle>`-backed cache - `MethodHandles.lookup().unreflectConstructor(ctor)` resolved once per distinct `Constructor` (there's only a handful total, one per Zeta event type with a registered Forge-style wrapper, so the cache stays tiny), then `handle.invokeWithArguments(args)` on every call thereafter. `ctor.setAccessible(true)` is called defensively before unreflecting, matching what reflection already implicitly allowed for this exact `Constructor` instance (it already worked via `newInstance` before this fix, so accessibility was never the blocker). Scoped `side="CLIENT"` in `neoforge.mods.toml`, same reasoning as the ScorchedGuns fix: only the client FPS symptom is targeted here, no server TPS complaint has been raised, and `ForgeEventsRemapper` is shared/common code (no `.client` subpackage) so this avoids touching the dedicated server's copy of the same class at all.
